The main classes

Discord owns one HTTP client, one part factory and the gateway connection. Parts such as Guild and Channel hold repositories of their children, and every repository is a cached collection that reads and writes through the same HTTP client.

A REST request

Every request, whether it comes from a repository, a part or $discord->getHttpClient() directly, joins the queue of its route's bucket. The bucket waits while Discord says the route is exhausted, and the client keeps at most five requests in flight. Interaction callbacks are not bound by the global limit, so they skip the queue.

sequenceDiagram
    autonumber
    participant App as Your code
    participant Repo as Part or repository
    participant Http as Http
    participant Bucket as Bucket, one per route
    participant Driver as Driver, React or Guzzle
    participant API as Discord REST API
    App->>Repo: $guild->channels->save($channel)
    Repo->>Http: post(Endpoint, attributes)
    Http->>Bucket: queueRequest() puts the request in its route's bucket
    Bucket->>Bucket: wait while X-RateLimit-Remaining is 0
    Bucket->>Http: hand the request over
    Note over Http: at most 5 in flight, interaction callbacks skip the queue
    Http->>Driver: runRequest(Request)
    Driver->>API: HTTPS request
    API-->>Driver: response and X-RateLimit headers
    alt 429 Too Many Requests
        Driver-->>Http: 429 with retry_after
        Http-->>Bucket: RateLimit, global or for this route
        Bucket->>Bucket: queue the request again and retry after retry_after
    else 502 or 525
        Http->>Driver: send it again
    else 2xx
        Driver-->>Http: response
        Http-->>Bucket: remember limit, remaining and reset-after
        Http-->>Repo: decoded JSON
        Repo->>Repo: Factory builds or fills the Part, then cache->set()
        Repo-->>App: the promise resolves with the Part
    else any other status
        Http-->>App: the promise rejects, with NotFoundException, NoPermissionsException, …
    end

A gateway event

The gateway sends compressed frames over one WebSocket. Discord inflates each one, decodes the payload and routes dispatches through Handlers to an Event class. That class updates the cache and returns the part your listener receives. Events that arrive before init are held back until the guilds have loaded.

sequenceDiagram
    autonumber
    participant GW as Discord gateway
    participant WS as WebSocket
    participant D as Discord
    participant H as Handlers
    participant E as Event handler, e.g. MessageCreate
    participant C as Repositories and cache
    participant L as Your listeners
    GW->>WS: frame, zlib-stream or plain JSON
    WS->>D: handleWsMessage(Message)
    D->>D: buffer until the frame ends in 00 00 FF FF, then inflate
    D->>D: processWsMessage(), emit('raw'), remember the sequence number
    alt op 0, DISPATCH
        D->>H: getHandler(t)
        H-->>D: handler class and alternative event names
        opt before init, except GUILD_CREATE and GUILD_DELETE
            D->>D: hold the packet until init
        end
        D->>E: handle(d)
        E->>C: cacheGet(), build Parts, update the caches
        E-->>D: the new Part, and the old one for updates
        D->>L: emit(t, [new, discord, old])
        opt MESSAGE_CREATE that mentions the bot
            D->>L: emit('mention')
        end
    else op 1, 7, 9, 10 or 11
        D->>D: heartbeat, reconnect, invalid session, hello or heartbeat ACK
    end

Listen for any event in the list with $discord->on(Event::MESSAGE_CREATE, fn (Message $message, Discord $discord) => …). The gateway events map lists them all.
